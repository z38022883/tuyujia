# 账号角色分类功能方案（v0.1）

> **状态**：2026-11-03 待评审。
> 需求：将患者账号与家属（照护者）账号区分标注，并按角色适配界面。
> **范围界定**：本期只做**角色标注 + 界面适配**（方案 A），不做账号绑定、不做家属远程查看患者数据（列入 P5 后续）。
> **设计原则**：角色 = **默认视角**，不是硬隔离。真实场景常见"一人一机、家属代操作"，任何角色都保留全部功能入口，角色只决定首页排序/弱化与默认视角。

---

## 1. 背景与结论

- 现状：`users` 集合仅有 `_openid / nickname / avatar`（`cloudfunctions/login/index.js` 首登自动注册），无角色概念；患者功能（表达/康复/中医）与照护者功能（接收/家属指导）混排在同一首页，靠用户自行分辨。
- 本期结论：
  1. `users` 文档新增 `role` 字段（`''` 未标注 / `patient` 患者 / `family` 家属），云端为唯一事实源，本地缓存随 `tuyujia_user` 同步；
  2. 新增角色选择页（仿程度选择页样式），接入首页首检门禁链（可「暂不选择」跳过，不阻塞）；
  3. 首页按角色**排序 + 弱化**功能卡片（患者→表达置顶、家属→接收置顶），不隐藏任何模块，头部加角色徽标可快捷切换；
  4. 我的页增加角色设置行与角色标签；
  5. 存量用户（无 role）一切保持现状，仅引导一次。
- 患者程度档案（`useProfileStore`）**不受角色影响**：两种角色都需要程度（表达词板与接收展示都按程度裁剪），程度门禁保持现状。

## 2. 角色定义

| 角色 | 值 | 主体是谁 | 高频功能 | 首页置顶 | 首页弱化 |
| --- | --- | --- | --- | --- | --- |
| 患者 | `patient` | 患者本人（或以患者为主的设备） | 表达 / 康复训练 | 表达 | 接收（照护者工具） |
| 家属 | `family` | 家属 / 照护者 | 接收 / 康复照护指导 | 接收 | 表达 |
| 未标注 | `''`（缺省） | — | 全部功能 | 现状顺序不变 | 无 |

- 未标注态 = 向后兼容态：存量用户升级后与现状完全一致，仅首页一次性引导。
- 角色只影响**展示层**（排序、徽标、文案），不影响任何数据读写链路；收藏/历史/云端同步均与角色无关。

## 3. 总体流程

```
首次启动（新用户）
  └─ 首页 onShow 首检链：无 severity → 程度页（现状不变）
       → 有 severity 且无 role 且未关闭过引导 → 角色页 → 选患者/家属 → 建档回首页
       → 「暂不选择」→ 记 dismissed 标记 → 回首页（不再强弹）
日常启动（有 role）
  └─ 首页 = 功能卡片按角色排序 + 头部角色徽标（点徽标 → 角色页改档，即时生效）
存量用户（无 role）
  └─ 升级后首次进首页：首检链弹一次角色页（可暂不选择）→ 之后静默
```

- 门禁链实现：`home/index.tsx` 现有 `onShow` 首检（无 profile → `reLaunch` 程度页）后追加一段：`无 role 且 dismissed 标记不存在 → reLaunch 角色页`。dismissed 存本地 key `tuyujia_role_prompt_dismissed`（不走 reLaunch 死循环的关键：暂不选择时写入该标记）。
- 角色修改即时生效：首页模块排序由 `role` 派生（useMemo），改档回首页自动重排，无需重启。

## 4. 各页面适配规格

### 4.1 角色选择页（新页 `pages/role/index`）

- 标题「选择账号角色」；副文案「请选择本机主要使用者，可随时在"我的"页修改」。
- 2 张大卡（复用程度页卡片样式）：
  - 患者 👤 蓝：图符表达 / 康复训练为主，接收工具放后
  - 家属 👪 绿：照护者视角，接收/展示工具置顶，康复含家属指导
- 页脚按钮：「保存并返回」+ 次按钮「暂不选择」（仅首检强弹场景显示；从我的页进入时不显示）。
- 保存 → 写本地 + 云端 → `reLaunch` 回首页。

### 4.2 首页（`pages/home/index.tsx`）

> 2026-11-04 修订：排序+弱化实测感知弱（"鸡肋"），改为**主功能大卡**方案（§9-1 拍板结果）。

| 维度 | patient | family | 未标注 |
| --- | --- | --- | --- |
| 主功能大卡 | 「表达」占整行大卡置顶，带「患者常用」角标（蓝） | 「接收」占整行大卡置顶，带「家属常用」角标（绿） | 无大卡，现状网格 |

- 主卡实现：`ROLE_PRIMARY` 映射（`'':null / patient:'express' / family:'receive'`），主卡从 `MODULES` 派生，剩余卡片 = `MODULES` 去掉主卡后的原顺序。
- 不隐藏、不弱化任何入口（家属也要偶尔帮患者用表达板；患者设备上家属也会用接收）。

### 4.3 我的页（`pages/mine/index.tsx`）

- 用户卡：昵称下方加角色小标签（患者/家属，未标注不显示）。
- 「患者程度」区上方新增「账号角色」卡片行：显示当前角色 → 点击进角色页（预选当前值，无「暂不选择」按钮）。
- 顺手迁移：mine 页现有 `useState` + 手动 `storage` 缓存 user 的逻辑迁到 `useUserStore`（P1 建立），消除各页各自管 user 的重复。

### 4.4 康复页（本期不改，P4 可选）

- `pages/rehab/family/index`（家属指导）现为独立入口按钮。家属角色的适配（进入康复页时自动突出家属指导入口 / 首页康复卡片 desc 按角色换文案）成本低，但为控制本期范围，列 P4 可选项（见 §9 待拍板 3）。

## 5. 数据模型与云函数

### 5.1 数据模型

- `types/index.ts`：`export type UserRole = '' | 'patient' | 'family'`；`User` 增加 `role: UserRole`。
- 注册默认值：login 云函数注册分支补 `role: ''`（与 avatar 默认空串同风格）；查询分支原样返回文档（含 role），前端自动带上，**login 云函数其余逻辑不动**。
- 存量文档无 role 字段 → 前端统一 `user.role ?? ''` 兜底，不要求回填。

### 5.2 新云函数 `updateUser`

- 输入 `event`：`{ role?: UserRole }`（nickname / avatar 预留同函数，白名单校验，非法值直接报错）。
- 行为：`openid` 由调用上下文注入，`where({_openid}).update({role})`，仅允许改本人文档。
- 输出：`{ code, message, data: { user: 更新后文档 } }`。
- 上线顺序：**先部署 updateUser 云函数，再发前端版本**（老前端不调用它，新前端依赖它）。

### 5.3 前端状态层（新 `store/useUserStore.ts`）

- `state`: `{ user: User | null }`；`load()`（读 `tuyujia_user` 缓存）、`setUser(u)`（写缓存+state）、`setRole(role)`（乐观更新本地 + `callFunction('updateUser')`，失败回滚并 toast）。
- 不新增 storage key：复用现有 `tuyujia_user`（User 对象多一个 role 字段，旧缓存缺 role 按 `''` 兜底）。

## 7. 实施阶段

- **P0 方案评审**：本文档拍板（进行中），确认 §9 待拍板 4 项。
- **P1 数据与状态层**（约 1 天）：`updateUser` 云函数 → login 注册默认值 → types → useUserStore → app.tsx 接线 → mine 页迁移 useUserStore（行为不变回归）。云函数先行部署验证。

- **P3 首页角色适配**（约 0.5~1 天）：排序映射与弱化样式 → 角色徽标 → 切档即时生效验证。
- **P4 兼容与打磨**（约 0.5 天）：存量用户（无 role 文档）全链路回归；改档后排序/徽标/我的页同步即时性；真机走查（含弱化卡片可点性）；（可选，若拍板）康复页家属视角适配。
- **P5 后续（不在本期）**：账号绑定（邀请码/扫码，家属远程查看患者表达与康复记录）；多患者管理；治疗师/医生角色；家属操作引导页。

合计约 **3~3.5 人天**（不含 P5）。

## 8. 风险与注意

- 新增页面后需**清 DevTools 缓存**再编译（rehab/level 页同款坑）。
- 云函数上线顺序：updateUser 未部署时新前端改角色会报错 → `setRole` 失败回滚 + toast 兜底，属可接受降级，但仍应先发云函数。
- 首检链顺序：程度门禁在前、角色在后——程度页保存后经 `shouldPromptRole()` 直达角色页（已消除两连跳闪屏）；首页门禁仅兜底存量用户。
- ~~弱化卡片仍可点入是刻意设计，评审时勿按"bug"处理。~~（弱化方案已废弃，改主功能大卡）
- `useUserStore` 与 mine 页旧 user 逻辑并存窗口要短：P1 迁移完成前不要先在 home 读 role，避免双源不一致。
- 旧版本前端不受影响：无 role 字段的读写路径全部向后兼容。
